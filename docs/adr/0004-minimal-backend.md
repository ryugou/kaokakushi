# バックエンドを最小構成にする

## Status

Accepted

## Context

上位仕様書 21 章は、自前バックエンドに次を想定していた。

- `POST /v1/installations`（匿名インストール ID の発行）
- `POST /v1/entitlements/apple/verify` / `POST /v1/entitlements/google/verify`（購入検証）
- ストア通知の受信と権限管理
- `GET /v1/config`（リモート設定）
- `POST /v1/diagnostics`（診断）

一方、仕様 14.5 は不正利用防止のためだけの端末固有識別子や過剰な個人情報の収集を禁じており、仕様 21.6 はバックエンド障害で編集処理を停止させないことを求めている。

購入検証とストア通知の受信は RevenueCat iOS SDK が担える。加工処理は端末内で完結しており、サーバーへ画像を送る経路は存在しない。

## Decision

**自前サーバーは 2 本のエンドポイントのみとする。**

| エンドポイント | 内容 |
| --- | --- |
| `GET /v1/config` | 無料枠、一括処理上限、トライアルクレジット数、トリアージ閾値、履歴の容量上限、スタンプの保存解像度、広告表示頻度、更新誘導、障害中の機能停止フラグ |
| `POST /v1/diagnostics` | 利用者が明示的に同意した場合のみ受信 |

実装は Rust + Axum。`/v1/config` は静的 JSON と ETag による配信とする。

**実装しないもの**

| 対象 | 理由 |
| --- | --- |
| `POST /v1/installations` | 匿名インストール ID は RevenueCat の App User ID と兼用する。仕様 21.4 の要件（Keychain 保存、広告 ID を利用者 ID にしない、ハードウェア識別子を収集しない）は満たされる |
| 購入検証 API | RevenueCat が担う |
| ストア通知の受信 | 同上 |

**サーバー側の設定署名（Ed25519）も v1 では実装しない。** 端末上の改変は `ProtectedBlobStore` の HMAC で防ぐが、CDN やバックエンドの侵害には対応しない。設定の内容が枠数と表示に限られ、金銭や個人情報へ直結しないためである。**脅威モデルとして範囲外**と記録する。

## Consequences

- **サーバーが応答しないことがアプリの停止を意味しない。** リモート設定の取得に失敗した場合は last-known-good、それも無ければバンドル済み既定値を使う。更新誘導は「取得できなければ更新なし」へ倒す（アーキテクチャ設計書 10 章）
- リモート設定は無料枠や強制更新を変更できるため、last-known-good を平文で保存できない。`ProtectedBlobStore` へ HMAC 付きで保存する（設計書 10 章）
- 安全性の中核（確認画面、全顔初期マスク、ファイル検証、コミットジャーナル、未受け渡し出力の保護）は、**対応する設定キー自体を `RemoteConfig` に持たせない**。フラグを既定で有効にするのではなく、フラグを存在させない
- 診断は自由形式の JSON を受け付けず、型付きの許可フィールドだけを受ける。サーバー側でも未知フィールドを拒否する（設計書 9.2 / 10 章）
- サーバーが保持するのは診断データのみで、保存期間は 30 日とする
