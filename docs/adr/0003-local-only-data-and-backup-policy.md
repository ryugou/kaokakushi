# 端末内完結とバックアップ対象外の徹底

## Status

Accepted

## Context

本アプリが端末へ置くものには、処理中の未加工の顔画像、未受け渡しの加工済み出力、顔領域を含む履歴、カスタムスタンプ実体、加工後サムネイル、購入状態・クォータ台帳（`app.db` の平文行）が含まれる。

「選択した写真は端末内で処理されます」という商品説明を掲げている以上、未加工の顔画像や顔領域を含む履歴を OS のクラウドバックアップへ移すことは、この説明と一貫しない。

利用者データ（DB、スタンプ、サムネイル）をバックアップ対象に含めるかは、当初は未決だった。

## Decision

**アプリが所有する DB・画像をすべてバックアップ対象外とする。**

`db/`（`app.db`）・`working/`・`outputs/` と一時ファイルに加えて、**`stamps/` / `thumbnails/` も対象外**とする。

理由は 4 つ。

| 理由 | 内容 |
| --- | --- |
| 商品説明との整合 | 「選択した写真は端末内で処理されます」と述べている以上、顔領域と加工済みサムネイルを OS のクラウドへ移すのは一貫しない |
| 復元の同時点性 | DB と画像ファイルが同じ時点で復元される保証がない。参照はあるが実体が無い状態が起こりえる |
| 参照の失効 | 別端末では写真ライブラリ参照（`ProjectSourceLocator`）が意味を持たない。履歴を復元しても再編集できない |
| 復旧 Saga の増加 | 「復元されたが実体が欠けている」経路を v1 で増やさない |

実行時状態を復元してはいけない理由は別にある。`ExportJob` を別端末へ復元しても対応する一時ファイルは存在せず、素材（`WorkingSourceRecord`）も見つからないため、復元された途端に処理を続行できない。

**将来バックアップする場合は、OS による生ファイルのバックアップではなく別設計とする。** DB・スタンプ・サムネイルを 1 つの検証可能なアーカイブとして書き出し、復元時に整合を検査する形にする。生ファイルの部分復元は、上記の同時点性の問題を解決できない。

## Consequences

- **利用者への明示が必須になる。** 設定画面と初回起動時に「履歴とマイスタンプはこの端末内にのみ保存されます。アプリの削除や端末の変更では引き継がれません」を記載する
- SQLite の rollback journal を確実に除外するため、DB を専用ディレクトリへ置く配置が必要になる（[アーキテクチャ設計](../architecture.md) の 7.4）
- **バックアップ方針と保護クラスが統一された結果、DB をファイル単位で分ける理由が消えた**（[ADR 0002](0002-grdb-and-single-database.md)）
- `isExcludedFromBackup` は一般的なファイル操作で `false` へ戻りうるため、ディレクトリへ一度設定するだけでは足りない。**すべてのファイル生成を `ManagedFileStore` へ通し、保存のたびに設定して読み返す**（[アーキテクチャ設計](../architecture.md) の 7.3）
- 再インストール後は `UsageLedger` が `Missing` となり、新規台帳が作られる。無料枠が戻ることは仕様 14.5 が許容している
- 処理中ファイルは `tmp/` ではなく `working/` へ置く。`tmp/` は OS がいつでも削除でき、キューの再起動復元が成立しなくなる（[アーキテクチャ設計](../architecture.md) の 7.4）
